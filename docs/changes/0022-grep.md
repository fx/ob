# 0022: Grep

## Summary

Add exact-text search over the files on disk: REST `POST /v1/vaults/:slug/grep` and the read-only MCP tool `grep`, matching a literal substring or a regular expression line by line in text files and returning path, line, column, and line text, with hard limits and a guarantee that a pathological regex cannot stall the server. Implements [REST API › Grep](../specs/rest-api/index.md#grep) and the `grep` row of [MCP Server › Tool surface](../specs/mcp-server/index.md#tool-surface).

**Spec:** [REST API](../specs/rest-api/), [MCP Server](../specs/mcp-server/)
**Status:** complete
**Depends On:** 0014, 0018, 0019

## Motivation

`search` ranks Markdown chunks by meaning. It cannot answer "where exactly does this string appear": hybrid retrieval returns the most relevant chunks, not every occurrence, it does not cover non-Markdown text files, and it gives no line numbers to aim a `patch_file` edit at. Agents currently page through `list` and `read_file` every candidate to find a literal string.

### Behavior owned by the specs

[REST API › Grep](../specs/rest-api/index.md#grep) owns the request and response shapes, which files are searched and in what order, line semantics, every limit and its value, truncation, and the no-stall guarantee; its scenarios are this change's acceptance criteria. [MCP Server](../specs/mcp-server/index.md#tool-surface) owns the tool input, description, read-only hint, and scoped-session rule.

### What this change owns

- **Isolation of regex evaluation.** Matching MUST run off the request-serving event loop so that the time budget is enforced by terminating the evaluation, not by checking a clock between lines — a single catastrophic `RegExp.exec` never returns to such a check.
- **Process-wide concurrency cap.** At most two greps MUST run at once; further calls wait for a slot in FIFO order. The 5-second budget starts when the request arrives and the wait counts against it, so a call whose budget runs out in the queue leaves it and returns the spec's empty `time` result. A request that is cancelled (the HTTP client disconnects, or MCP cancels the call) MUST leave the queue if waiting, or terminate its worker if running.
- **Read containment.** Grep reads every file through 0019's `guardedRead` (parent-chain check, `O_NOFOLLOW` open, `fstat` regular-file check), per the spec's containment precondition for reads; a failure skips the file. A parent swapped in the instant between the check and the open is outside the spec's threat model, so no directory-descriptor walk is added. The walk's `Dirent` symlink skip alone is not enough, because a concurrent folder move can swap a walked directory for one containing a symlink between the walk and the read.
- **Scoped sessions.** Scoping comes from the service core walking `vault(slug).root`, which the scoped deps already replace with the scope root; tests MUST show a scoped grep never reads outside the scope and returns scope-relative paths. `prefix` is matched literally against those scope-relative paths with no translation, so `prefix: ""` searches the whole scope rather than being rejected; a test covers it.

## Design

`grep(deps, slug, args)` in `src/vault/grep.ts` validates the arguments (compiling the regex once on the main thread with the `u` flag, plus `i` for `ignoreCase`, so a syntax error is an immediate `invalid_input`; a literal pattern is escaped into an equivalent regex so both modes share one matcher), then hands the scan to a Bun `Worker` (`src/vault/grepWorker.ts`) with the vault root, prefix, pattern source, flags, limits, and budgets:

- The worker walks with the 0019 walk (so ordering, hidden and symlink skipping match `list`), filters to `isTextPath`, reads each file through `guardedRead` with `maxBytes: 1 MiB` (size checked with `fstat` on the opened descriptor and the read bounded at the cap plus one sentinel byte that only detects growth, so a file over the cap, or growing past it mid-read, is skipped and counted in `filesSkipped`, and no more than 1 MiB is ever searched), skips it if a NUL byte appears, decodes with `TextDecoder` (replacement on), splits lines, matches each line as the whole input of one `RegExp` evaluation (so anchors bind to the line, and the first match, zero-length or not, gives the column), keeps a ring buffer of `context` lines before and collects `context` after, and windows long lines. When it finds a match beyond the first `limit` it does not post it: that match is a sentinel proving more exist, never emitted to the main thread and never counted. The worker completes the `limit` matches it has (their `after` context), counts the file the sentinel was found in as scanned (the spec's `limit` stop), and posts a final checkpoint with `reason: "limit"`. It also stops on the byte budget, or when it finishes, and posts the result.
- The main thread races the worker's messages against a deadline timer. On the deadline it calls `worker.terminate()` — which stops a running `RegExp` mid-evaluation — and answers with the complete matches the worker had streamed so far. The worker posts every match as soon as it is complete, meaning its `after` context has been read or the file ended (batched at most 50 at a time, and flushed before matching each new line once a batch is pending), so a timeout in the middle of a file still keeps that file's earlier complete matches, as far as they reached the main thread in a checkpoint before the deadline. The result is a prefix of the full result, as the spec requires. Every message the worker posts is a checkpoint: it carries the new matches and the cumulative `filesScanned` and `filesSkipped` as of that moment. The worker posts a counters-only checkpoint when a file finishes or is skipped without new matches, and it never counts a file before that file finishes. The main thread accumulates the match deltas of every checkpoint it receives and keeps the latest checkpoint's counters. On termination it answers with the accumulated matches through the last checkpoint received before the deadline, plus that checkpoint's counters, so a counters-only last checkpoint never discards earlier matches. They come from the same moment by construction: the counters cover the files finished or skipped by that checkpoint, while the accumulated matches can include complete matches from the file still in progress, which no counter counts yet. Both may lag the worker's true progress by whatever messages were still in flight, exactly as the spec states. `truncated` and `reason` are set by the main thread from why the scan ended (the worker's final message for `limit` and `bytes`, the deadline for `time`), and nothing else in the response is computed by the worker.
- The semaphore wait is raced against the same deadline and the request's abort signal.
- A small FIFO semaphore in the same module enforces the two-grep cap.
- Adapters: `GrepBody` / `GrepInput` / `GrepResponse` in `src/schemas/grep.ts`, the route in `src/http/routes/grep.ts`, the tool in `src/mcp/tools/grep.ts` passing `{ readOnlyHint: true }`.

### Decisions

- **Decision:** Contain ReDoS by isolating and terminating evaluation, not by restricting the regex language or swapping engines.
  - **Why:** JavaScript's backtracking `RegExp` cannot be interrupted from the same thread, so any in-thread budget is advisory against a catastrophic pattern. A terminable worker turns the 5-second budget into a hard bound with no new dependency, and keeps ECMAScript syntax that agents already write.
  - **Alternatives considered:** A linear-time engine (an RE2 binding or WASM build) — rejected for v1: a native or WASM dependency in the image, and a dialect that silently differs from what callers expect (no lookaround, no backreferences). Rejecting "dangerous" patterns statically — rejected: no static check catches every super-linear pattern.
- **Decision:** Literal by default, case-sensitive by default.
  - **Why:** Matches `grep -F` expectations for the common "find this exact string" use, and spares callers from escaping regex metacharacters in pasted text.
- **Decision:** One result per matching line, with the first match's column.
  - **Why:** `grep -n` semantics; a line is the unit an agent reads and edits.
- **Decision:** Search the disk, not the index.
  - **Why:** The index holds only Markdown, chunks it, and can lag writes; grep has to be exact and cover all text files.
- **Decision:** No cursor (see the spec's open question); callers narrow with `prefix`.

### Non-Goals

- Multiline patterns, replace (sed), searching PDFs or binaries, user-supplied regex flags, glob include/exclude filters.

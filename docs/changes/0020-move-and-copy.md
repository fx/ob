# 0020: Move and Copy

## Summary

Add `move` (mv) and `copy` (cp) for files and folders: REST `POST /v1/vaults/:slug/paths/*path:move` and `:copy`, MCP `move` and `copy`. A move goes to an exact destination: a folder move, or a file move with `overwrite: true`, is one atomic rename, while a default file move publishes the destination without replacing anything and then removes the source. It refuses to clobber unless asked, re-embeds moved notes, and by default rewrites the internal links that pointed at what moved. Implements [REST API › Path operations](../specs/rest-api/index.md#path-operations) (move and copy), the whole of [Link rewriting](../specs/rest-api/link-rewriting.md), the move indexing rule in [Vault Indexer › Public surface](../specs/vault-indexer/index.md#public-surface), and the `move` / `copy` rows of [MCP Server › Tool surface](../specs/mcp-server/index.md#tool-surface).

**Spec:** [REST API](../specs/rest-api/), [MCP Server](../specs/mcp-server/), [Vault Indexer](../specs/vault-indexer/)
**Status:** draft
**Depends On:** 0019

## Motivation

There is no way to rename a note or folder through ob. Clients fall back to read + write + delete, which loses modification times, cannot move a folder in one step, leaves the old path searchable until the watcher catches up, and breaks every link to the note — Obsidian desktop rewrites links only for renames it performs itself, never for renames it receives through Sync. Copy has the same read-then-write workaround and no folder form.

### What this change owns

- **New error code.** `already_exists` MUST be added to `ErrorCode` / `ERROR_CODES` in `src/errors.ts` as `AlreadyExistsError` (carrying the conflicting path), mapped to HTTP 409 in `src/http/errors.ts`, and covered by the closed-set test.
- **Two-path locking.** A helper that takes the per-path lock for several keys at once MUST acquire them in one canonical order (sorted, de-duplicated) so no two operations can each hold a lock the other is waiting for. A folder operation locks the folder's own path, so any two ob operations targeting the same destination — file or folder, move or copy — contend on the same key.
- **Canonical lock keys everywhere.** Today `withPathLock` (`src/vault/lock.ts`) is keyed `${slug}:${path}` with the caller's raw path. In a scoped session that path is scope-relative, because `scopeDeps` (`src/mcp/scope.ts`) swaps the descriptor's `root` for the scope root rather than rewriting paths. It is also not normalized. So a scoped `patch_file` of `x.md` and an unscoped `PATCH` of `agents/a/x.md` (or `a.md` and `./a.md`) take different locks on the same file. This change MUST key every lock — move, copy, the rewriter, and the existing `writeFile`, `patchFile`, `appendFile`, and `deletePath` — by the absolute resolved path `safeJoin` returns. That path is the same for scoped and unscoped callers and already canonical.
- **Canonical paths.** Source and destination are canonicalized as the spec's shared rule states (trailing `/`, empty and `.` segments dropped) before the equality check, the descendant check, lock keys, `M`, and every response path; `assertSafeRelativePath` accepts `.` segments, so without this `./a.md` → `a.md` would pass the equality check.
- **One indexable-path rule.** This change relies on a single index set, so it MUST implement [Vault Indexer › Indexable paths](../specs/vault-indexer/index.md#indexable-paths) as one exported `isIndexablePath` (replacing the scanner's `shouldIgnorePath` + `isMarkdownFile` pair) and use it in the scanner, the watcher, the pipeline, and every direct `reindex` (moves, copies, link rewrites, and the existing writes). Today the scanner skips symlinks only implicitly, because a symlink `Dirent` is neither `isFile()` nor `isDirectory()`. The watcher has no symlink check, and chokidar follows symlinks by default, so a folder moved in with a symlink to an outside note can get that note indexed through watcher events. The watcher MUST set `followSymlinks: false`, and the pipeline MUST re-check the path (chain `lstat`, `O_NOFOLLOW` open) immediately before it reads a file, rejecting a non-indexable path.
- **`reindex` reports failure.** Today `src/indexer/pipeline.ts` catches read, chunk, embed, and store failures, logs them, and counts them in `IndexerStatus.errors`, but `Indexer.reindex` still resolves. So `tryReindex` reports `indexed: true` for a note whose index entry is missing or stale. `reindex` MUST reject on those failures, per [Vault Indexer › Public surface](../specs/vault-indexer/index.md#public-surface). Because `writeFile`, `patchFile`, and `appendFile` share `tryReindex`, this deliberately changes their `indexed` too: it becomes `false` whenever the index update failed, which is what the REST spec has always said it means.
- **Per-vault move serialization.** A per-vault move mutex MUST be held by every `move` from before it takes its path locks until its link-rewrite phase ends. Nothing else takes this mutex, and it is always taken first, so it cannot deadlock with path locks. Copies, deletes, and writes do not take it. Link rewrites take each referring note's lock individually after the move's own locks are released.
- **Check under the lock, publish without replacing.** Every destination existence and type check MUST be (re)done while holding both locks, immediately before publishing; a check made before the locks are taken is advisory only. File publishes without `overwrite` MUST use the hard-link no-replace primitive wherever the filesystem supports it, and fall back exactly as the spec's [concurrency and failure guarantees](../specs/rest-api/index.md#path-operations) state where it does not.
- **Containment precondition.** The spec's [containment precondition](../specs/rest-api/index.md#path-operations) is the rule: every filesystem call that creates, writes, links, renames, or removes a path is immediately preceded by `assertNotSymlinkEscape` over the full parent chain of every path it touches. The only exemption is the spec's: targets strictly inside this call's own freshly created hidden UUID staging folder. The staging folder's own creation, final rename, and removal are not exempt. All such calls MUST go through the single `guarded` helper described in Design, and no move, copy, or rewrite code may call those `fs` functions directly. This is stricter than `writeFile` today, which runs `assertNotSymlinkEscape` once before taking its lock and then `mkdir -p`s, writes its temp file, and renames without re-checking. The residual window after each check is the same as `writeFile`'s and is outside the spec's threat model.
- **Owned-only cleanup.** Every failure path conforms to guarantee 3 of the spec: it removes only this call's exclusively created, uniquely named hidden temp files and staging folders, and the parent folders this call recorded creating (deepest first, `rmdir` only). It never unlinks, renames over, or recursively removes anything else.
- **Scoped link context.** In a scoped MCP session the service core sees the scope root as the vault root, but link resolution must use vault-relative paths over the whole vault. The scoped deps wrapper (`src/mcp/scope.ts`) MUST therefore hand the move service the real vault root and the scope prefix for link resolution only, and the rewriter MUST refuse to write any note outside the scope. No tool result may carry the prefix (link text inside notes is content and is exempt, per the spec).

## Design

### The `guarded` helper

`src/vault/guarded.ts` exports `guarded(root, paths, op)`: it runs `assertNotSymlinkEscape(p, root)` for every path in `paths` (each checks the whole parent chain), then immediately calls `op()`. Each `fs.mkdir`, `fs.open(…, "wx")` / write, `fs.link`, `fs.rename`, `fs.unlink`, `fs.rmdir`, and `fs.rm` that move, copy, or the link rewriter performs is wrapped as `guarded(root, [...touched], () => fs.x(...))`, with both paths of a link or rename listed. Staging-interior calls use `stagingInterior(stagingRoot, op)` instead. It asserts the target is strictly inside a staging root this call created, which makes the exemption explicit and greppable, and skips the chain check. A lint-level test asserts that `src/vault/paths.ts`, `src/vault/links.ts`, and the copy code call no mutating `fs` function except through these two helpers.

### Move

`movePath(deps, slug, path, { destination, overwrite, updateLinks })` in `src/vault/paths.ts`:

1. Take the vault's move mutex. Validate both paths (`safeJoin` + `assertNotSymlinkEscape`) and canonicalize them; reject `destination === path` and, for a folder, `destination` under `path/`. These are lexical and need no lock.
2. Take the locks for the source and destination keys (canonical order).
3. Under the locks, `lstat` both. Missing source → `not_found`. Existing destination → `already_exists` unless `overwrite` and both are files. Nothing before this point decides the outcome.
4. If links are to be updated, snapshot the vault's visible file set (`F_before`) with the 0019 walk, still under the locks and before anything moves.
5. Create the destination's missing parents with `ensureParents(dst)`, still under the locks and only now that the checks passed: find the deepest existing ancestor, then create each missing level top-down with `guarded(root, [level], () => fs.mkdir(level))` (non-recursive), so every level's chain is checked immediately before its own `mkdir`. A level is recorded only when this call's `mkdir` created it. On `EEXIST`, `lstat` the component: a real directory was created by someone else, is not recorded, and the walk continues; a symlink or a file is `invalid_path`. Any later failure calls `removeCreatedParents()`, which `rmdir`s the recorded levels deepest first and stops at the first one that refuses (`ENOTEMPTY`, `EEXIST`, `ENOENT`), leaving it and everything above it.
6. Publish, still under the locks. Every `link`, `rename`, and `unlink` below runs through `guarded` with both `src` and `dst`. A check hit is `invalid_path`, followed by `removeCreatedParents()`, whose `rmdir`s are each `guarded` too:
   - **File, no `overwrite`:** `fs.link(src, dst)`. `EEXIST` maps to `already_exists`; then `removeCreatedParents()` runs and nothing else has changed. On success, `fs.unlink(src)`. The hard link keeps the inode, so bytes and modification time are preserved. If `unlink(src)` fails, nothing is undone: `dst` is not unlinked, because an outside writer may already have replaced it and this call cannot prove the file there is still its own link. The call fails with `internal`, both paths keep the file (the same end state as a crash between the two steps), and the watcher indexes `dst`.
   - **File, `overwrite: true`:** `fs.rename(src, dst)`, one atomic replace. `EISDIR` (the destination became a folder) maps to `already_exists`.
   - **Folder:** `fs.rename(src, dst)` onto the destination step 3 confirmed absent. `ENOTEMPTY` / `EEXIST` / `ENOTDIR` map to `already_exists`. The empty-directory window against outside writers is the spec's guarantee 2; Node and Bun expose no `RENAME_NOREPLACE`.
   - **No hard links.** If `link` fails with `EPERM`, `ENOTSUP`, or `EOPNOTSUPP` (the filesystem refuses hard links), the publish falls back to `fs.rename(src, dst)` right after re-running the under-lock destination check, and logs a warning once per vault. This is the spec's degraded guarantee 2 for files; ob's own operations stay fully serialized by the locks, and the move still works.
   - **Parent removed underneath.** If a publish fails with `ENOENT` because a parent this call found existing was removed in the meantime by another call's cleanup, steps 5–6 run once more; a second `ENOENT` is an `internal` error.
   - `EXDEV` cannot occur within one vault tree; if it does, it surfaces as `internal` after `removeCreatedParents()`.
7. Build `M` (old → new for every moved file the 0019 walk lists, so hidden entries and symlinks that travelled with a folder are not in it) and `F_after`. `M` drives link rewriting. Index steps use two different predicates. Reindexes (step 10) use the full `isIndexablePath` on the new path. Drops use no predicate at all: after the rename every old path is absent and so fails `isIndexablePath`, and dropping a path with no rows is a no-op, so gating a drop on it would leave stale rows. For a file move, while still holding the source lock, drop the old path's rows under the drop guard (unless an indexable note exists at the old path). For an `overwrite` move onto a destination, while still holding the destination lock, also drop the destination's old rows (the one drop of a path that still exists, immediately before that path is reindexed), so the replaced content is never served even if step 10 fails. Then release the path locks (the move mutex stays held).
8. Index, folder moves: for each old path in `M` (no indexability check), take that path's lock, and drop its rows unless an indexable note exists at the path now — the indexer spec's drop guard, applied to what exists now, not to the old path. If an indexable note exists, a writer recreated it and reindexed it under the same lock, so its rows are fresh; anything else there (a symlink, a folder) has its rows dropped. The drops come after releasing the folder locks so that file keys are never acquired out of the canonical order.
9. Links: run the rewriter (below); it reindexes every note it writes.
10. `tryReindex` every indexable new path in `M` the rewriter did not already reindex, with the scanner's bounded concurrency (4). `indexed` is `true` iff at least one indexable path was reindexed (here or by the rewriter) and every required drop (steps 7–8) and reindex succeeded, so `tryDrop` now reports failure instead of only logging it. A move of only binaries or of an empty folder reports `false`, and hidden entries and symlinks never count either way. Release the move mutex.

### Link rewriter

`src/vault/links.ts`, pure apart from its file I/O:

- **Parsing.** Parse each referring note with the remark setup the chunker already uses (`remark` + `remark-gfm` + `remark-frontmatter`) only to obtain the source offsets of `code` and `inlineCode` nodes; scan the raw text outside those ranges with a wikilink regex and a CommonMark inline-link destination scanner. Working on raw offsets, never on a re-serialized AST, is what keeps every untouched byte identical.
- **Resolution.** `resolveLink(link, sourcePath, files)` implements the spec's four steps over an index built once per move: a case-folded `Map` from full path to files and one from `"/" + basename-suffix` to candidates, so each lookup is O(1) and a move costs one pass over the vault's Markdown bytes plus one resolution per link.
- **Rewriting.** For each link compute `t0`, `expected`, `t1`, and the resolution step before and after; build the replacement linkpath per the style table; check it resolves to `T`; splice replacements back-to-front by offset; write the note atomically (exclusive hidden temp file + rename, every call through `guarded`, as Copy › Note rewrites describes) and `tryReindex` it, under the note's lock. A note whose text changed between scan and write (detected by comparing its bytes under the lock with the bytes scanned) is re-scanned once; if it changed again it is reported in `failed`.
- **Scope.** The rewriter's candidate notes are the Markdown files of `F_after` inside the write root (the scope root in a scoped session, the vault root otherwise); `F_before` / `F_after` always cover the whole vault.

### Copy

`copyPath(deps, slug, path, { destination, overwrite, recursive })`:

- **File.** Take the source and destination locks, do the existence and type checks under them, and run `ensureParents(dst)` as for a move. Read the source through `guardedRead` (a mismatch is `invalid_path`). Write the bytes to a hidden temp sibling `.<dst-name>.<uuid>.tmp`, opened exclusively (`wx`) through `guarded`, so the call provably owns it (hidden, so `list`, the watcher, and the indexer never see it). Publish through `guarded` with `tmp` and `dst`: without `overwrite`, `fs.link(tmp, dst)` (`EEXIST` → `already_exists`) then a `guarded` `fs.unlink(tmp)`; with `overwrite`, `fs.rename(tmp, dst)`, and if that replaced an existing file, drop the destination's old rows (the indexer spec's overwritten-destination case) while still holding the destination lock, before the reindex below (only the reindex applies `isIndexablePath`). The temp removal on a failure path is `guarded` as well. On a failure before the publish, remove the temp file and `removeCreatedParents()`. After a successful publish nothing is rolled back: if `unlink(tmp)` fails, the hidden temp file is left, the failure is logged, and the copy still succeeds. **No hard links:** if `link(tmp, dst)` fails with `EPERM`, `ENOTSUP`, or `EOPNOTSUPP`, the fallback is a `guarded` `fs.rename(tmp, dst)` of the call's own temp file, after re-running the under-lock destination check, with the same once-per-vault warning as a move. It is never `rename(src, dst)`: a copy never moves, renames, or removes its source. The `ENOENT` retry is the move's. Reindex if Markdown.
- **Folder.** Take the destination lock just long enough to check the destination is absent and run `ensureParents(dst)`; release it. Create the hidden staging folder `.<dst-name>.<uuid>.copy` with a `guarded` non-recursive `mkdir`, so the call provably owns it. Then recreate the source inside it with the 0019 walk, reading each source file through `guardedRead` (a mismatch fails the copy with `invalid_path`) and counting the hidden entries and symlinks skipped. Every folder and file written inside the staging folder is created with `mkdir` / `wx` (never following an existing entry) through `stagingInterior`: these calls are the spec's one exemption. Then take the destination lock again, re-check that the destination is absent, and `fs.rename` the staging folder onto it through `guarded` with both paths (`ENOTEMPTY` / `EEXIST` / `ENOTDIR` → `already_exists`), with the same guarantee-2 empty-directory window as a folder move. On any failure, including a lost race, `fs.rm` the staging folder recursively through `guarded` (the staging root is checked; it and everything in it were created by this call), then `removeCreatedParents()`, and rethrow, so no destination appears. Then reindex the copied Markdown files with concurrency 4.
- **Note rewrites** are not destination publishes: they replace the note they read under its lock, exactly as `patch_file` does, with the outside-writer window the [Link rewriting](../specs/rest-api/link-rewriting.md#applying-rewrites) spec records. The rewriter does not call `writeFile`. It reads each referring note through `guardedRead` (a mismatch reports the note in `failed` with `invalid_path`) and writes through `guarded`: the temp file's `wx` creation, its `rename` over the note, and its removal on failure are each `guarded` with the note's path and the temp path.

### Decisions

- **Decision:** Exact destination (`mv -T`), never "into an existing folder".
  - **Why:** One request shape means one thing. With into-folder magic, `move a.md archive` means two different things depending on whether `archive/` exists, and the client cannot tell which happened without re-listing.
  - **Alternatives considered:** Unix default semantics. Rejected for the ambiguity above.
- **Decision:** Refuse to clobber by default; a folder never replaces or merges, even with `overwrite`.
  - **Why:** Agents retry and guess paths; a default that silently replaces a note destroys data with no undo. Merging folders has no single right answer for conflicting children.
- **Decision:** `updateLinks` defaults to `true`.
  - **Why:** Matches Obsidian desktop's default, and is the only way a rename through ob does not silently break the vault for the person reading it in Obsidian.
- **Decision:** Hard link plus unlink for a no-overwrite file publish, rather than `rename` after a check.
  - **Why:** `rename` replaces an existing file without failing, so check-then-rename loses whatever appeared at the destination after the check — another ob call (closed by the lock) or Obsidian Sync (not closable by any lock). `link` is the only portable no-replace publish Node and Bun expose for files. The cost is an instant where the file is visible at both paths, which loses nothing.
  - **Alternatives considered:** `copyFile` with `COPYFILE_EXCL` then unlink for moves — rejected: it copies the bytes and resets the inode and modification time. Checking under the lock alone — rejected: it closes the race between ob calls but not against outside writers.
- **Decision:** Outside writers are cooperating; adversarial filesystem writers are out of the threat model.
  - **Why:** Obsidian Sync and the user's own tools are the only other writers in a supported deployment. A party with raw write access to the vault directory can already delete or replace anything without going through ob, and ob is explicitly not an authorization boundary. Guarding cleanup against such a party (inode tracking, `openat`-style descriptor walks) would add machinery that protects nothing that party could not destroy directly.
  - **Exception kept:** vault containment is checked immediately before every create, write, link, rename, and remove (bar the staging interior), because "never read or write outside the vault root" is a standing MUST that every other operation already enforces with `assertNotSymlinkEscape`.
- **Decision:** Cleanup removes only what the call provably created; leftovers beat loss.
  - **Why:** A cleanup that deletes "its own" destination or parents without proof can delete what an outside writer put there in the meantime — the exact loss the no-replace publish exists to prevent. Exclusive creation (`wx`, non-recursive `mkdir` of a uuid name, recorded parent levels) is the proof; `rmdir` adds a second guard because it refuses a folder that is no longer empty.
  - **Alternatives considered:** Undo the link when `unlink(src)` fails — rejected: the file at `dst` may no longer be the call's link. Leave all created parents on failure — rejected: a 4xx would then change the vault.
- **Decision:** Serialize moves per vault rather than revalidating links at rewrite time.
  - **Why:** A rewrite is computed from `F_before` / `F_after`; a second move that runs before the first finishes rewriting makes those snapshots stale, so chained moves (`a → b`, then `b → c`) could rewrite `[[a]]` to `[[b]]` after `b` is gone. Holding a per-vault mutex from lock acquisition through the rewrite phase makes each move see the tree the previous one left, at the cost of moves in one vault running one at a time — they are rare, user-initiated operations.
  - **Alternatives considered:** Re-resolve every link against the current tree under the note lock at rewrite time. Rejected: it needs a fresh whole-vault file set per note (or a live index kept in step with every concurrent write) and still cannot tell which of two concurrent moves a link should follow.
- **Decision:** Move first, then rewrite; per-note rewrite failures are reported, not rolled back.
  - **Why:** The move is the operation asked for and is complete once the destination is published and the source removed; link rewrites touch many notes and cannot be made atomic as a group. Rolling the move back after some notes were rewritten would need its own rollback of those rewrites, which can fail too. Reporting exactly which notes failed lets the caller retry them with `patch_file`.
  - **Alternatives considered:** Pre-validate every rewrite before renaming. Rejected: it narrows but cannot close the window, because a note can become unwritable or change between check and write.
- **Decision:** Drop and reindex moved notes rather than renaming rows in place.
  - **Why:** `embed_text` starts with the note's path, so renamed rows would keep vectors and FTS tokens for the old path, and the scanner would never fix them (it short-circuits on an unchanged `sha256`). Re-embedding is the only way the index ends up as a fresh scan would build it.
  - **Alternatives considered:** Rename rows and keep vectors (cheap, silently stale). Rejected for the reason above.
- **Decision:** Scan the disk for links, not the index's `links` column.
  - **Why:** The index stores only normalized wikilink targets — no Markdown links, no offsets, no style — and can lag the disk.
- **Decision:** Rewrite only links whose target moved or whose note moved.
  - **Why:** The scope the user agreed; correcting unrelated links whose resolution a move changed is recorded as an open question in the spec.
- **Decision:** Folder copy is staged and renamed into place.
  - **Why:** A partial copy left by a mid-copy failure is indistinguishable from a complete one to a caller listing the destination.

### Non-Goals

- Moving or copying across vaults.
- Link rewriting on copy or delete, links by alias, links in canvas files.
- Making folder operations atomic with respect to concurrent writes inside the folder (per-file serialization only, as the spec states).
